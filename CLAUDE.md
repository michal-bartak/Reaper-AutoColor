# CLAUDE.md — Reaper AutoColor

Guidance for Claude Code (claude.ai/code) working in this repository. Read this
first, then `docs/DECISIONS.md` and `docs/RESEARCH.md` before changing anything.

## What this is

A REAPER (ReaScript / Lua 5.4) tool that colours **tracks, items, regions and
markers from their names** — plain substring, glob, or real regular expressions.
One ordered rule list per object kind; within a kind the first rule that matches
wins, so precedence works like firewall rules.

SWS's Auto Color does case-insensitive substring only and has no item support;
that gap is why this exists.

## Work from `~/GitRepo/AutoColor`, never from the REAPER Scripts folder

`<REAPER resource path>/Scripts/MXM_AutoColor` is a **symlink** into
`Reaper/Scripts/MXM_AutoColor` here, for development sync only. Git commands run
from the Scripts path are scoped to that subdirectory — `git ls-tree` is
prefix-relative and the repo looks as though it has lost most of its files.
Always `cd ~/GitRepo/AutoColor` first.

No build step for the scripts themselves: REAPER runs the `.lua` files where
they sit. `make` alone lists every target.

## Module map

Entry points are thin; `lib/` holds everything. Each module's header comment
explains its own design — read it rather than inferring from the code.

| Module | Role |
|---|---|
| `lib/apply.lua` | plan / prune / commit. `plan()` is pure; `commit()` is the only thing that writes |
| `lib/targets.lua` | the **only** module that knows how REAPER stores names and colours |
| `lib/matcher.lua` | substring / glob / regex front end; glob compiles to regex, so one engine |
| `lib/regex.lua` | hand-written pure-Lua regex engine (parser → program → backtracking VM) |
| `lib/colors.lua` | canonical form is `0xRRGGBB`; native (OS-dependent) values are never persisted |
| `lib/config.lua` | the JSON rule set, plus the ExtState revision counter |
| `lib/rules.lua` / `lib/predicates.lua` | the rule record, and the non-name filters that *narrow* it |
| `lib/autoloop.lua` | the background auto-apply engine and its cost model |
| `lib/gui/*` | ReaImGui window; `app.lua` owns state, the rest draw |

**The GUI's preview is `plan()` with no commit** — the same code path, not an
approximation. Keep it that way; it is what makes the preview honest.

## Things that will bite

- **The GUI and the auto-toggle hold their Lua state for as long as they run.**
  After editing `lib/`, the user must close the window and re-run it, and toggle
  auto off/on. One-shot actions pick up changes immediately. This has produced
  "your change did nothing" more than once — say it when handing over a fix.
- **Verify REAPER API claims; do not assert from memory.** The ReaImGui
  reference is installed at `<resource path>/Data/reaper_imgui_doc.html` — grep
  it. The core ReaScript reference is *not* installed, but the binary carries the
  whole API table: `strings -a /Applications/REAPER.app/Contents/MacOS/REAPER`.
  Two confident assumptions have already been wrong (master-track colour;
  `Col_ModalWindowDimBg`). That is also how `B_UISEL` was found after I claimed
  marker selection state did not exist.
- **For pixels and layout, measure — do not reason.** Add a throwaway probe to
  `dev/` that prints real coordinates to the REAPER console, have Michal run it,
  delete it in the fixing commit. Three layout questions were settled that way in
  one session, each with a different cause than the hypothesis.
- **Michal runs things in REAPER and reports back precisely.** Treat that as
  authoritative over reasoning from source.
- The user's rules live at `<resource path>/MXM_AutoColor/config.json` —
  deliberately outside `Scripts/`, gitignored, never in the repo.
- The version exists twice: `Color/MXM_AutoColor.lua` (`@version`, for ReaPack)
  and `lib/about.lua` (what the About dialog shows). A unit test keeps them from
  drifting.

## Tests

```bash
make test        # == ./tests/run.sh
```

Needs a standalone Lua (`brew install lua`) and python3. Runs entirely outside
REAPER — the REAPER and ReaImGui APIs are mocked, and everything writes under
`tests/.tmp/`. Suites: unit (via `MXM_AutoColor_RunTests.lua`), integration,
autoloop, gui, render, plus a differential regex fuzz that diffs `lib/regex.lua`
against Python's `re` over three fixed seeds.

`run.sh` resolves everything from one `NC` variable, so a layout change needs
exactly one line updated there. CI runs the suite on every push and PR
(`.github/workflows/tests.yml`, on Lua 5.4 to match REAPER).

## Docs

Astro + Starlight in `docs/`, published to GitHub Pages on pushes to `main` that
touch `docs/`.

```bash
make docs                    # build + serve at http://localhost:4321/Reaper-AutoColor/
make docs-dev                # live-reload, for writing
make docs-diagrams-verify    # diff the computed diagrams against the real apply.lua
```

- **`docs/DECISIONS.md` records what was tried and rejected; `docs/RESEARCH.md`
  records external facts verified against source rather than documentation.** Do
  not re-derive them, and keep them current when a decision changes.
- **The colouring diagrams under `docs/src/assets/usage/diagrams/` are
  generated**, not drawn — `docs/scripts/diagrams.py` computes every square from
  a port of `lib/apply.lua`. Never hand-edit an SVG there.
  `make docs-diagrams-verify` runs the same scenarios through the real
  `apply.plan()` and diffs; that check caught the port doing an RGB lerp where
  `colors.lua` interpolates in HSL.
- **Screenshots have no fallback.** The placeholder generator was removed
  (2026-09-21) once every shot was real, so a page referencing a missing image
  fails the Astro build with `[ImageNotFound]`. Add the figure and the file in
  the same change.
- `make icon` re-renders every icon output from `icon/icon.svg`. Deliberately not
  a prerequisite of the docs build — the outputs are committed and the master
  changes about never.

## Releasing (ReaPack)

Publishing is a **separate, explicitly approved step** — never folded into a
code change. Full rules live in the ReaPack notes; the ones specific to this
repo:

- `Color/MXM_AutoColor.lua` is the manifest and the category. Package identity is
  `UNIQUE(remote, category, package)` — renaming the category directory, the
  manifest filename, or the index `name=` orphans everyone's install.
- **A version is only re-cut when the manifest file itself changes.** The
  manifest is in `Color/` and the code in `Reaper/`, so fixing a shipped file
  publishes nothing: `reapack-index` says "Nothing to do!" and the version stays
  pinned to an older commit. Bump `@version` (or `--amend` with an `@about` /
  `@changelog` edit), then verify with `git show <pinned sha>:<file>`.
- `reapack-index` needs `/opt/homebrew/opt/ruby/bin:/opt/homebrew/lib/ruby/gems/4.0.0/bin`
  on PATH, and **dies without a TTY** (`IO#getch` → `Errno::ENODEV`) — pass
  `--no-commit` and commit `index.xml` yourself. Careful: `-C` is
  `--[no-]commit`, so bare `-C` *enables* committing.
- It scans git history, so a *downgrade* does not remove higher versions —
  trim unwanted `<version>` blocks by hand; the `commit=` marker makes the trim
  stick.
- `@provides` globs use `FNM_PATHNAME`: `lib/*.lua` and `lib/gui/*.lua` are
  separate lines. The `> ../MXM_AutoColor/` retargeting is what drops the
  category from the install path (ReaPack clamps traversal at the index name).
- **A `.lua` anywhere below the repo root carrying a `@version` tag becomes a
  package candidate.** Shipped scripts under `Reaper/Scripts/` must not carry a
  ReaPack header — keep it in the manifest only.
- **The merged index is a required second step.** Clients import
  `michal-bartak/ReaPack`; this repo's `index.xml` is only an input to
  `merge-index.py` there. Until that runs and is pushed, a new version reaches
  nobody.

## Writing: short, and in the right place

Prose is the thing I most often have to cut. Default to fewer words.

- **UI text is the tightest.** A tooltip is two or three short lines. A dialog
  states what will happen and stops. Neither explains *why* something works the
  way it does, and neither restates what the manual covers.
- **Say it once, in one place.** Reasons and background belong in `docs/` --
  the user-facing pages for how to use it, `DECISIONS.md` and `RESEARCH.md` for
  why. Not in a tooltip, not repeated across three files.
- **Don't pad a reply.** Answer what was asked. No preamble, no summary of what
  I just did if the diff already shows it, no listing of options I'm not taking.
- **Code comments earn their place** by explaining what the code cannot: a
  constraint discovered the hard way, why an obvious alternative was rejected.
  Not a paraphrase of the line below.
- **Impersonal and purposive, not conversational.** State the fact, then the
  purpose with "to ...". Write "Configuration stored outside the scripts
  location, to prevent overwriting on update" -- not "Rules live outside
  Scripts/, so updating never touches them." No chatty verbs, no reassurance
  clauses, no addressing the reader where a statement will do. This is
  strictest in the changelog, UI strings and commit subjects.
- **Leave out anything the manual covers or the reader already assumes.** "The
  configuration window needs ReaImGui 0.10+" is worth saying; "every other
  action works without it" is not -- it follows, and the manual has it.
- **Commit messages: subject plus a short paragraph.** What changed and why, in
  a few sentences. Not a walkthrough of the diff.
- **The changelog is for users, in short bullets.** Group related changes into
  one bullet. Name the feature, not the module. Internals -- a refactor, a new
  file, a test -- do not appear at all unless the user can see the difference,
  and then it is described as what they see. Anything that makes them act
  (a moved path, a rebind, a setting that resets) goes last, as prose.
- When a change makes a paragraph redundant, delete it in the same commit.

## Working agreement

- When asked to *see* something (an icon, a layout, any visual): render a
  preview into the scratchpad and stop. Do not create repo files, edit the
  manifest, or bump a version in the same turn. Three separate approvals, in
  order — approve the design, approve wiring it in, approve committing and
  regenerating the index.
