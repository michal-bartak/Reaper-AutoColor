## Repository layout

```
Reaper/                     mirrors REAPER's resource path; this is what gets installed
  Scripts/MXM_AutoColor/
    MXM_AutoColor_*.lua actions you add to REAPER's Action List
    lib/                    the engine; lib/gui/ is the only part that uses ImGui
  Data/toolbar_icons/       the toolbar icon, at 1x, 150 and 200
Color/                      the ReaPack manifest, and nothing else; the directory
                            name is the ReaPack category the package is listed
                            under -- not part of the install path
dev/                        author-only probes, deliberately not shipped
tests/                      runs outside REAPER against a mocked API
icon/                       icon.svg, the master every icon output is rendered from
docs/                       this site (Astro + Starlight)
docs/DECISIONS.md           why it is built this way, and what was tried first
docs/RESEARCH.md            verified external facts: SWS, ReaImGui, REAPER prefs
index.xml                   generated by reapack-index; never edit by hand
```

`Reaper/` mirrors the resource path, so installing by hand is a single merge copy and the ReaPack
package is the same tree. The manifest sits outside `Reaper/`, in `Color/`, so it never deploys into
REAPER; it pulls the shipped files out of `Reaper/` by absolute path. `.reapack-index.conf` keeps
`.github`, `dev`, `docs`, `icon` and `tests` out of the package.

`Color/` has to stay where it is: ReaPack's package identity is (index name, category, package
name), and the category *is* the manifest's directory, so renaming it would orphan every existing
install. It does not have to show up on disk, though — every `@provides` line retargets with `../`,
which ReaPack resolves and clamps at the index name, so the package installs to
`Scripts/MXM Scripts/MXM_AutoColor/` and the installed tree matches `Reaper/`.

:::tip[Read the two notes first]
`docs/DECISIONS.md` and `docs/RESEARCH.md` record what was tried and rejected, and external facts
checked against source rather than documentation. They exist so nobody has to re-derive them.
:::

## Tests

`MXM_AutoColor_RunTests.lua` runs from REAPER's Action List and prints a summary to the ReaScript
console. It touches no project state and never writes your config.

The full suite runs **outside** REAPER, against a mocked API:

```bash
brew install lua     # once; 5.4 or newer
make test            # or ./tests/run.sh
```

Expect `ALL GREEN`. The runner's exit status is meaningful, so it drops straight into CI or a
pre-commit hook. It covers the engine, the action scripts end to end, the background loop, the GUI
logic and its drawing paths — against a mock REAPER and a stub ImGui — plus a differential fuzz of
the regex engine against Python's `re`. See
[`tests/README.md`](https://github.com/michal-bartak/Reaper-AutoColor/blob/main/tests/README.md).

:::caution[Reloading changed code]
The window and the auto-toggle hold their Lua state for as long as they run. After editing anything
under `Reaper/Scripts/MXM_AutoColor/lib/`, close the window and re-run it, and toggle auto off and
on. One-shot actions pick up changes immediately.
:::

## These docs

The site is [Astro](https://astro.build/) + [Starlight](https://starlight.astro.build/), in `docs/`:

```bash
make docs          # build and serve at http://localhost:4321/Reaper-AutoColor/
make docs-dev      # live-reload dev server, for writing
make docs-build    # static build into docs/dist/
```

`make` with no target lists them all. The targets are thin wrappers around `npm` in `docs/`, so
`cd docs && npm install && npm run dev` does the same thing.

Pages are Markdown under `src/content/docs/`, and the sidebar is the `sidebar` array in
`astro.config.mjs`. A new page has to be added in both places.

### The icon

`icon/icon.svg` is the only hand-drawn icon file. Everything else renders from it:

```bash
make icon
```

| Output | Why there |
|---|---|
| `Reaper/Data/toolbar_icons/mxm_toolbar_autocolor.png` (+ `150/`, `200/`) | Part of the install payload, so it ships with the scripts |
| `docs/public/favicon*.png`, `favicon.svg` | The site's tab icon |
| `icon/autocolor-128.png` | The README mark |

The master stays outside `Reaper/` because it is a source file, not something REAPER installs; the
renders go inside it because they are. The toolbar strips are the interesting output: REAPER wants a
90×30 PNG holding three 30×30 cells — normal, hover, pressed — and finds hi-DPI copies by the same
filename in `150/` and `200/`. `docs/scripts/icon.mjs` carries the reasoning for the margin and the
state treatment, both settled by measuring REAPER's own icons rather than by taste.

### Diagrams

The colouring diagrams under `docs/src/assets/usage/diagrams/` are generated, not drawn.
`docs/scripts/diagrams.py` holds one scenario per diagram — the tracks, the rules and the options —
and computes every colour with a port of `lib/apply.lua`:

```bash
make docs-diagrams           # redraw them all (docs-dev and docs-build run it too)
make docs-diagrams-verify    # run the same scenarios through the real apply.lua and diff
```

Edit a scenario and the picture follows the tool. `docs/scripts/diagrams_verify.lua` is what keeps
the port honest: it feeds the scenarios to the real `apply.plan()` and prints the colours it chose,
and the verify target diffs the two. It needs a standalone lua, and says so and exits cleanly
without one.

### Screenshots

Every screenshot is taken by hand: the window is a ReaImGui script inside REAPER, so there is
nothing to drive from CI. They live under `docs/src/assets/<section>/`, and the pages reference them
relatively, so replacing one is "save over the file, rebuild" — no markdown edit.

A page that references an image which is not there fails the build, with
`[ImageNotFound] Could not find requested image`. Add the figure and the file together.

:::note
Images in Markdown go through Astro's image pipeline, which converts them to `webp` and stamps the
width and height, so a PNG straight from REAPER is the right thing to commit.
:::

## Publishing

`.github/workflows/deploy-docs.yml` builds `docs/` and deploys it to GitHub Pages on every push to
`main` that touches the directory. GitHub Pages needs a paid plan for private repositories, so the
workflow skips itself while the repo is private and starts working the moment it is public.

`site` and `base` in `astro.config.mjs` encode the published URL
(`https://michal-bartak.github.io/Reaper-AutoColor/`). Both need updating if the repository is
renamed.
